# S01 Word — скорость до видимого просмотра (замеры + выбор)

Дата: 2026-10-05. Образцы: синтетические DOCX, только сгенерированный
текст (`s01_small` 1 стр., `s01_medium` 5 стр. + таблица + картинка,
`s01_large` 30 стр. с таблицами). Клиентские документы не использовались.
Замеры движками репозитория локально, холодный старт — свежий кэш.

## Сравнение маршрутов до видимого результата (холодный старт)

| Маршрут | small (1 стр.) | medium (5 стр.) | large (30 стр.) |
|---|---|---|---|
| DOCX → HTML (первый видимый iframe) | 51 мс | 119 мс | 504 мс |
| COM → PDF (конвертация целиком) | 6 882 мс | 7 259 мс | 13 306 мс |
| PDF → PNG150 первая страница | 178 мс | 229 мс | 173 мс |
| PDF → PNG150 все страницы | 315 мс | 1 618 мс | 9 049 мс |
| COM → PDF → PNG150 первый видимый PNG | ~7,1 с | ~7,5 с | ~13,5 с |
| COM → PDF → PNG150 всё до показа | ~7,2 с | ~8,9 с | ~22,4 с |
| HTML → PNG | недоступен (см. ниже) | — | — |

Тёплый повтор (кэш диска): HTML ~12 мс, COM-manifest ~17 мс,
PNG первых страниц — хит кэша, полностраничный хит ~21 мс.

PNG 150 dpi читаем (проверено визуально на синтетике);
HTML читаем по построению. PNG 96 dpi быстрее на ~70 мс/стр.,
но для Word оставлен стандарт 150/300 (вопрос разрешений — этап S03).

## Выводы и выбор

1. Для DOCX самый быстрый читаемый путь — существующий быстрый
   HTML (`/api/word/preview`, 50–500 мс): быстрее COM-маршрута
   примерно в 100 раз на холодную. Миниатюра — тот же кэшированный
   HTML в карточке (паттерн Excel), большой просмотр — тот же HTML.
2. COM → PDF → PNG остаётся для DOC/RTF (единственный путь) и как
   фолбэк + HQ-страницы 300 dpi. Прогрессивность: сначала первая
   страница, остальные в фоне той же эпохи.
3. HTML → PNG технически недоступен: браузерного снимка в проекте
   нет (поиск: html2canvas/headless/playwright/puppeteer — 0
   совпадений). Потребовал бы новую тяжёлую зависимость — не тянем,
   сообщаем здесь.
4. Время готового HTML со временем готового PNG не сравнивалось —
   только время до видимого результата по каждому маршруту.

## Реализация (эта ветка, только `app/frontend/app.js`)

- DOCX в ленте: `fetchWordHtmlCard` → карточка `WORDHTML` с iframe
  того же кэшированного HTML (классы `excel-book-preview`
  переиспользованы, своего CSS нет); клик — большой HTML-просмотр;
  ошибка — откат на существующий COM-путь (`skipWordHtmlFast` против
  повторного цикла). Нативное открытие — кнопка существующего
  большого HTML-просмотра.
- COM-путь Word: два прохода (`firstPageOnly: true`, затем `false`)
  в одной эпохе; счётчики — только по полному проходу; дедуп
  повторной первой страницы — существующим `pageKey`.
- Защита от поздних ответов: `epoch` на карточке, проверка эпохи в
  `showWordPreviewFast` после fetch (опциональный параметр, старое
  поведение без него не меняется), существующие `renderEpoch`/
  `AbortController` затронуты только добавлением.
- Сервер не менялся (все конечные точки уже существовали).
  Постоянный дисковый кэш, переключение эпохами, открытие оригинала
  (`/api/open-file`) — без изменений.

## Проверка

- `node --check app/frontend/app.js` — чисто.
- Все 31 python-тестов репозитория — OK.
- Серверная прогрессия на синтетике 10 стр.: `firstPageOnly`
  436 мс (1 стр.) → полный проход 1 424 мс с `cacheHitPages=1`,
  URL первой страницы совпадает (дедуп фронта сработает);
  повтор first-only — 20.8 мс хит.
- Браузерный E2E нового фронта не выполнялся (один короткий
  локальный тест читаемости/PNG — выполнен на синтетике).

## Ограничения

- DOC/RTF холодная первая миниатюра по-прежнему ждёт полный COM
  (неустранимо без смены конвертера); выигрыш — только растровая
  стадия (~9 с на 57 стр.).
- Визуальная приёмка нового фронта пользователем не проводилась.
